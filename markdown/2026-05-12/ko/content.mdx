## 문제

Claude Code를 터미널 탭 여러 개에 띄워놓고 일하다 보면, 어느 세션이 지금 무엇을 하고 있는지 알 수 없습니다.

- 어떤 탭은 도구를 실행하며 열심히 돌아가고 있고
- 어떤 탭은 **권한 승인을 기다리며 멈춰 있고**
- 어떤 탭은 이미 끝났거나 죽어 있습니다

문제는 두 번째입니다. 승인을 기다리는 세션은 아무 소리도 내지 않습니다. 다른 일을 하다가 한참 뒤에 돌아와서야 "아, 여기서 멈춰 있었네"를 발견합니다. 그때까지 그 세션은 아무것도 하지 않고 있었습니다.

터미널을 하나씩 열어보는 것 말고 방법이 없을까. 화면 구석에 항상 떠 있으면서 모든 세션의 상태를 보여주는 것을 만들기로 했습니다.

## 무엇을 만들었나

macOS 데스크탑 위젯입니다. 항상 위에 떠 있는 280×360 반투명 패널에 실행 중인 모든 Claude Code 세션이 카드로 나열됩니다.

상태는 네 가지입니다.

| 상태 | 색 | 의미 |
| --- | --- | --- |
| working | 노랑 | 도구를 실행하며 작업 중 |
| waiting_permission | 주황 | **권한 승인 대기 — 내가 봐야 함** |
| done | 초록 | 작업 완료 |
| aborted | 회색 | 5분 이상 응답 없음 |

정렬은 시간순이 아니라 **우선순위순**입니다.

```ts
const PRIORITY = {
  waiting_permission: 0,
  working: 1,
  done: 2,
  aborted: 3,
};
```

시간순으로 정렬하면 방금 끝난 세션이 맨 위로 올라오는데, 그건 제가 볼 필요가 없는 정보입니다. 정작 봐야 할 "승인 대기"는 아래로 밀려납니다. 그래서 **나를 필요로 하는 것이 항상 맨 위**에 오도록 했습니다. 만든 목적 자체가 그거였기 때문입니다.

## 상태를 어디서 가져올 것인가

가장 먼저 정해야 했던 것입니다. Claude Code는 자신의 상태를 알려주는 API를 제공하지 않습니다. 두 가지 실마리가 있었습니다.

**1. Hook** — Claude Code는 특정 시점(도구 실행 전후, 권한 요청, 세션 종료 등)에 외부 명령을 실행해줍니다. 빠르고 정확합니다. 다만 앱이 켜지기 전에 시작된 세션은 알 수 없고, hook이 항상 오지도 않습니다.

**2. 세션 기록 파일** — `~/.claude/projects/` 아래에 세션마다 JSONL 파일이 쌓입니다. 느리지만 **모든 세션에 대해 항상 존재하는 근거**입니다.

둘 중 하나만 쓰면 각각의 약점이 그대로 남습니다. 그래서 **둘 다 쓰고 한 곳에서 합치기로** 했습니다.

<Mermaid>
{`flowchart TD
  CC["Claude Code 세션"] -->|"hook 실행 (stdin으로 JSON)"| CLI["hook-cli<br/>독립 Node 스크립트"]
  CLI -->|"HTTP POST (로컬)"| SRV["hook 서버"]
  SRV --> MAP[("메모리 상태 Map<br/>세션ID → 상태")]

  CC -->|"기록 파일 append"| JSONL[("~/.claude/projects<br/>*.jsonl")]
  JSONL -->|"파일 변경 감지"| WATCH["watcher"]

  MAP --> SCAN["scanProjects<br/>두 출처를 합치는 곳"]
  WATCH --> SCAN
  JSONL --> SCAN

  SCAN -->|"IPC push"| UI["렌더러 (React)"]`}
</Mermaid>

두 경로가 `scanProjects` 한 곳으로 모입니다. 여기서 기록 파일을 파싱한 결과와 hook이 남긴 메모리 상태를 세션 ID로 join합니다.

## hook이 앱을 어떻게 찾는가

여기서 문제가 하나 있었습니다. hook으로 실행되는 스크립트는 **Claude Code가 띄우는 짧은 수명의 별개 프로세스**입니다. 이 스크립트는 내 Electron 앱이 어디서 듣고 있는지 알 방법이 없습니다.

포트를 고정하면 간단하지만, 다른 프로그램이 쓰고 있으면 충돌합니다. 그래서 반대로 했습니다.

1. 앱이 켜질 때 **OS가 비어 있는 포트를 골라주게** 하고 (`listen(0)`, 로컬 주소에만)
2. 그 포트 번호를 `~/.claude/.pet-hook-port` 파일에 적어둡니다
3. hook 스크립트는 이 파일을 읽어서 어디로 보낼지 알아냅니다
4. 앱이 종료될 때 파일을 지웁니다

앱이 꺼져 있으면 hook 스크립트는 파일이 없는 것을 확인하고 **아무것도 하지 않고 즉시 종료**합니다.

이 부분이 중요했습니다. hook은 사용자의 Claude Code 세션 안에서 실행됩니다. 여기서 에러가 나거나 오래 걸리면 **제 위젯 때문에 남의 작업이 느려집니다.** 그래서 hook 스크립트는 성공하든 실패하든 타임아웃되든 항상 정상 종료하고, 등록할 때도 비동기로 5초 타임아웃을 걸어둡니다.

```ts
// 어떤 경로로 끝나든 exit(0) — Claude Code에 에러를 노출하지 않는다
req.on("error", () => process.exit(0));
req.on("timeout", () => process.exit(0));
```

## 기록 파일을 매번 다 읽지 않기

세션 기록 파일은 대화가 길어지면 수 MB까지 커집니다. 파일이 바뀔 때마다 전체를 다시 읽으면 앱이 점점 느려집니다.

그래서 **어디까지 읽었는지 바이트 위치를 기억**해뒀다가 새로 늘어난 부분만 읽습니다. 파싱도 마찬가지로, 이전 결과에 새 줄만 접어 넣는 방식입니다.

```ts
// 파일이 줄었으면 잘린 것이므로 처음부터 다시 읽는다
const start = size < lastOffset ? 0 : lastOffset;
```

파일이 갑자기 작아지는 경우(재작성이나 회전)를 처리하지 않으면 엉뚱한 위치부터 읽어서 깨진 JSON을 만나게 됩니다.

## 만들고 나서 고친 것

가장 인상 깊었던 버그입니다.

**주황색(승인 대기)에서 영원히 멈추는 세션이 있었습니다.**

원인은 이랬습니다. 권한 요청이 오면 hook이 `waiting_permission`으로 바꿔줍니다. 그리고 사용자가 거부하면 `PermissionDenied` hook이 와서 상태를 풀어줘야 합니다. 그런데 **일부 도구는 이 hook을 보내지 않았습니다.** 그러면 실제로는 이미 끝난 세션이 화면에서는 계속 "승인을 기다리는 중"으로 남습니다.

hook만 믿을 수 없다는 뜻이었습니다. 그래서 기록 파일을 교차 확인하게 했습니다.

<Mermaid>
{`flowchart TD
  A["hook 상태: 승인 대기"] --> B{"기록 파일에<br/>마지막 응답 이후<br/>도구 결과가 있나?"}
  B -->|"있음 = 실제로는 처리됨"| C["done으로 정정"]
  B -->|"없음 = 진짜 대기 중"| D["승인 대기 유지"]`}
</Mermaid>

도구 실행 결과가 기록에 남았다는 것은 그 도구 호출이 어떤 식으로든 끝났다는 뜻입니다. hook이 오지 않아도 이걸로 알 수 있습니다.

**두 출처를 합쳐둔 설계가 여기서 빛을 발했습니다.** 하나만 썼다면 이 버그는 고칠 방법이 없었습니다.

## 배포에서 배운 것

서명하지 않은 앱이라 macOS가 실행할 때마다 경고를 띄웠습니다. 특히 로그인 항목으로 자동 실행할 때 반복해서 나타났습니다.

이건 코드 문제가 아니라 **배포 조건의 문제**였습니다. 정식 해결책은 Apple 개발자 계정으로 서명 및 공증하는 것인데, 개인 프로젝트에 연 $99를 쓰긴 어려웠습니다.

그래서 앱이 시작할 때 자기 자신에게 붙은 격리 표시를 스스로 떼도록 했습니다. 근본 해결은 아니고, 조건이 바뀌면(서명하게 되면) 걷어내야 하는 코드입니다. 그 판단을 기록으로 남겨뒀습니다.

## 마치며

3일 동안 만든 작은 프로젝트였지만, 남은 것은 세 가지입니다.

**하나.** 믿을 수 없는 신호가 있으면 **믿을 수 있는 다른 신호와 교차 확인**할 수 있는 구조를 만들어두는 편이 낫습니다. hook만 썼다면 stuck 버그를 고칠 방법이 없었고, 기록 파일만 썼다면 반응이 느렸을 겁니다.

**둘.** 남의 프로세스 안에서 도는 코드는 **실패하더라도 조용히 실패해야** 합니다. 제 위젯이 안 뜨는 것보다 그것 때문에 Claude Code가 느려지는 게 훨씬 나쁩니다.

**셋.** 시작할 때 품었던 전제가 틀렸습니다. Claude Code가 터미널 UI를 React Ink로 만들었다는 걸 보고 "React가 웹을 벗어나 훨씬 넓은 곳까지 간다"고 생각해서 Electron을 골랐습니다. 그런데 막상 만들어보니 Electron의 Renderer는 Chromium입니다. React가 웹을 벗어난 게 아니라 **웹이 데스크탑 안으로 들어온 것**에 가까웠습니다. 실제로 이 프로젝트에서 웹과 달랐던 지점은 React가 아니라 그 바깥 — 프로세스 분리, IPC, 파일 접근 권한 — 이었습니다. 정작 "React 생태계가 넓다"의 증거로 삼으려던 React Ink는 아직 못 써봤고, 그건 여전히 숙제로 남아 있습니다.
