## The problem

When you run Claude Code across several terminal tabs, you can't tell what any given session is doing.

- One tab is running tools and working away
- One tab is **stopped, waiting for permission approval**
- One tab already finished, or died

The second one is the problem. A session waiting for approval makes no sound. You go do something else, come back much later, and only then notice it had been sitting there. The whole time, it did nothing.

I wanted a way to see that without opening each terminal. So I built something that sits in the corner of the screen and shows the status of every session at once.

## What it does

It's a macOS desktop widget — an always-on-top 280×360 translucent panel listing every running Claude Code session as a card.

There are four statuses.

| Status | Color | Meaning |
| --- | --- | --- |
| working | yellow | Running tools |
| waiting_permission | orange | **Blocked on approval — needs me** |
| done | green | Finished |
| aborted | gray | No response for 5+ minutes |

Sorting is by **priority**, not by time.

```ts
const PRIORITY = {
  waiting_permission: 0,
  working: 1,
  done: 2,
  aborted: 3,
};
```

Sorting by time puts the most recently finished session on top — which is exactly the information I don't need. The one thing I do need, "waiting for approval," gets pushed down. So **whatever needs me sits at the top**. That was the entire reason the thing exists.

## Where does the status come from?

This was the first decision. Claude Code doesn't expose an API for its own state. There were two available signals.

**1. Hooks** — Claude Code runs external commands at specific moments (before/after tool use, permission requests, session end). Fast and precise. But it can't see sessions that started before the app, and the hooks don't always arrive.

**2. Transcript files** — a JSONL file accumulates per session under `~/.claude/projects/`. Slower, but it's **evidence that always exists for every session**.

Using only one leaves its weakness in place. So I used both and **merged them in one place**.

<Mermaid>
{`flowchart TD
  CC["Claude Code session"] -->|"runs hook (JSON on stdin)"| CLI["hook-cli<br/>standalone Node script"]
  CLI -->|"HTTP POST (loopback)"| SRV["hook server"]
  SRV --> MAP[("in-memory state Map<br/>sessionId → status")]

  CC -->|"appends transcript"| JSONL[("~/.claude/projects<br/>*.jsonl")]
  JSONL -->|"file change"| WATCH["watcher"]

  MAP --> SCAN["scanProjects<br/>where both sources merge"]
  WATCH --> SCAN
  JSONL --> SCAN

  SCAN -->|"IPC push"| UI["renderer (React)"]`}
</Mermaid>

Both paths converge on `scanProjects`, which joins the parsed transcript facts with the hook-derived state by session ID.

## How the hook finds the app

There was a problem here. The hook script is a **short-lived, separate process spawned by Claude Code**. It has no way of knowing where my Electron app is listening.

A fixed port is simple but collides with whatever else might be using it. So I inverted it.

1. On startup, let **the OS pick a free port** (`listen(0)`, loopback only)
2. Write that port number to `~/.claude/.pet-hook-port`
3. The hook script reads that file to learn where to send
4. Delete the file on quit

If the app isn't running, the hook script sees no file and **exits immediately without doing anything**.

This mattered. The hook runs inside the user's Claude Code session. If it errors or hangs, **my widget slows down someone else's work.** So the hook script always exits cleanly — success, failure, or timeout — and it's registered as async with a 5-second timeout.

```ts
// Exit 0 on every path — never surface an error inside Claude Code
req.on("error", () => process.exit(0));
req.on("timeout", () => process.exit(0));
```

## Not re-reading the whole transcript

Transcript files grow to several megabytes as conversations get long. Re-reading the whole file on every change makes the app progressively slower.

So it **remembers the byte offset** it read up to and reads only what's new. Parsing works the same way — folding only the new lines onto the previous result.

```ts
// If the file shrank, it was truncated — start over
const start = size < lastOffset ? 0 : lastOffset;
```

Without handling the shrink case (rewrite or rotation), you'd read from the wrong offset and hit broken JSON.

## What I fixed afterward

The most instructive bug.

**Some sessions got stuck on orange (waiting for permission) forever.**

Here's why. When a permission request arrives, a hook flips the status to `waiting_permission`. When the user denies it, a `PermissionDenied` hook should arrive and release that state. But **some tools never sent it.** So a session that had actually finished stayed on screen as "waiting for approval" indefinitely.

Which meant hooks alone couldn't be trusted. So I made it cross-check against the transcript.

<Mermaid>
{`flowchart TD
  A["hook state: waiting for permission"] --> B{"Is there a tool result<br/>after the last response<br/>in the transcript?"}
  B -->|"yes = actually resolved"| C["correct to done"]
  B -->|"no = genuinely waiting"| D["keep waiting"]`}
</Mermaid>

A tool result appearing in the transcript means that tool call finished one way or another. That tells you what the missing hook didn't.

**This is where merging two sources paid off.** With only one, the bug would have had no fix.

## What distribution taught me

The app isn't signed, so macOS warned on every launch — especially when auto-starting as a login item.

That wasn't a code problem but a **condition-of-distribution problem**. The proper fix is signing and notarizing with an Apple developer account, and $99/year is hard to justify for a personal project.

So the app strips its own quarantine flag at startup. It isn't a real fix, and it's code that should be removed once the condition changes (once it's signed). I left that reasoning in the record.

## Wrapping up

Three days, 105 commits. About 1,700 lines, with no single file over 120.

Two things stayed with me.

**One.** When a signal can't be trusted, it's worth building a structure that can **cross-check it against a different, trustworthy signal**. Hooks alone couldn't fix the stuck bug; transcripts alone would have been slow.

**Two.** Code that runs inside someone else's process must **fail quietly when it fails**. My widget not appearing is far better than my widget slowing down Claude Code.

**Three.** The premise I started from was wrong. Seeing that Claude Code built its terminal UI with React Ink, I figured React reached far beyond the web, and picked Electron on that basis. But Electron's renderer is Chromium. React hadn't left the web so much as **the web had moved into the desktop**. What actually differed from the web here wasn't React but everything around it — process separation, IPC, filesystem permissions. And React Ink, the very thing that was supposed to prove the point, I still haven't touched. That one's still open.
