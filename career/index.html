API 계층 재설계 제안과 팀 단위 점진 전환

제안 및 이관

문제

Server Action 기반 API 계층에 세 문제가 겹쳐 있었습니다. 요청이 순차 처리되어 클라이언트에서 병렬로 묶어도 네트워크 워터폴을 피할 수 없었고, 빌드 시 생성된 액션 ID로 참조되어 배포 직후 구버전 클라이언트의 요청이 실패하는 Version Skew가 배포마다 발생했습니다. 일반 HTTP 요청이 아니어서 MSW 같은 서드파티 라이브러리와 호환이 떨어져 E2E와 스토리북이 각자 다른 방식으로 응답을 대신 만들고 있었습니다.

선택

기존 방식을 유지하면 변경은 가장 적지만, 워터폴이 Server Action의 요청 처리 방식 자체에서 오므로 사용법으로는 풀리지 않고 Version Skew와 모킹 문제도 남습니다. Route Handler로 바꾸면 세 문제는 풀리지만 zod와 TanStack Query 래퍼를 새로 만들어야 하고 타입 안정성에 별도 처리가 필요합니다. 그래서 기존 개발 구조와 다르지 않으면서 부가 기능을 갖춘 기술을 찾았습니다. tRPC는 기존 zod, TanStack Query를 그대로 쓰면서 HTTP 위에서 배치 병렬 요청과 캐싱을 지원하고 MSW도 그대로 동작해, 이를 교체 대상으로 제안했습니다.

실행

  • 트레이드오프를 정리해 제안하고 팀 방향으로 채택 — 도메인 단위로 점진 이관하고, 완료 후 기존 인프라를 전량 제거

  • 전환 후에야 가능해진 tRPC-MSW 모킹 환경을 구축해 E2E와 스토리북을 단일 핸들러 세트로 통합하고, 개발 서버에서도 모킹이 동작하게 구성

결과

  • 순차로 처리되던 초기 요청이 배치로 병렬 처리되면서, 로그인 후 첫 화면의 전체 데이터 요청 시간이 49% 감소

  • 배포 직후 요청이 실패하던 일이 사라졌고, 팀 전체 도메인 전환을 운영 중단 없이 완료. 신규 API는 핸들러 하나로 E2E와 스토리북이 함께 동작

인증 상태 관리 구조 재설계

단독 설계 및 구현

문제

클라이언트가 로그인 시점과 만료까지 남은 시간으로 만료 시각을 자체 계산해, 기기 시간 오차나 절전 모드 복귀 시 서버 기준과 어긋나 만료 응답을 받는 일이 반복됐습니다. 이를 막는 국소 대응 코드가 계속 늘고 있었고, ISMS 인증 준비로 세션 만료 정책을 명시적으로 정의하고 증빙해야 하는 요건이 더해졌습니다.

선택

클라이언트 계산에 여유 버퍼를 더하면 어긋남은 줄지만 기준이 클라이언트와 서버 둘인 원인은 그대로 남습니다. 짧은 주기로 세션을 폴링하면 기준은 서버 하나로 모이지만 아무 일이 없어도 인증 API 호출이 계속 생겨, 4.5만 사업자 규모에서 상시 비용이 정당화되지 않습니다. 문제의 원인이 기준이 둘이라는 점이므로 클라이언트에서 판단 자체를 없애고 서버의 거절에만 반응하는 쪽을 골랐습니다. 추가 호출 없이 기준이 하나가 됩니다.

실행

  • 만료 판단을 서버 응답 하나로 일원화해 클라이언트가 만료 시각을 계산하던 경로를 없애고, ISMS가 요구하는 세션 만료 정책을 코드 한 곳에 명시

  • 인증이 필요한 쿼리는 인증이 확정된 뒤에만 실행되게 해 비로그인에서는 인증 요청 자체가 나가지 않게 하고, 만료 확정은 서버의 명시적 거절에만 내려 서버 오류나 네트워크 오류가 로그아웃으로 번지지 않게 함

  • 기존 응답까지 모두 수용하는 구조로 만들어 백엔드가 교체 배포되는 중에도 문제가 없게 하고, 새 구조를 문서화해 팀의 기준으로 둠

결과

  • 기존과 신규 응답을 함께 수용한 덕분에 서비스 전체 인증 레이어를 무중단으로 교체

  • 흩어져 있던 만료 계산과 임시 대응 코드를 전량 제거

  • 비로그인 방문자의 인증 요청이 사라져 서버 리소스 확보

  • 세션 만료 정책이 코드 한 곳에 명시되어 업계 최초 ISMS 인증 획득에 기여

주요 페이지 SSR 구조 설계

단독 설계 및 구현

문제

주요 페이지들은 로그인 여부를 클라이언트 쿼리로 판단했고, 정산달력은 모바일과 데스크톱 레이아웃도 브라우저에서만 구분했습니다. 그래서 서버 HTML에는 스켈레톤과 GNB, 푸터만 담겼고, 구조화 데이터를 갖춘 페이지인데도 크롤러가 읽을 본문이 없었습니다.

선택

SEO가 중요한 주요 페이지들에는 인증 분기를 서버에서 미리 판단해야 했습니다. 처음에는 공식 문서의 표준 방식인 HydrationBoundary로 넘기려 했습니다. 하지만 사용자 정보는 상위 레이아웃에서 먼저 구독되고, HydrationBoundary는 이미 있는 쿼리의 반영을 effect로 미루기 때문에 서버 렌더에 반영되지 않았습니다. 경계를 루트 레이아웃으로 올리면 쿠키를 읽는 호출 때문에 모든 페이지가 동적 렌더로 바뀌고, 상위 소비자를 모두 서버 렌더에서 빼면 하나라도 빠뜨리는 순간 아무 경고 없이 스켈레톤으로 돌아가는 구조였습니다. 그래서 기존 쿼리에 값을 바로 넣는 initialData를 택했습니다. 인증을 확정한 뒤에도 정산달력은 뷰포트 분기 때문에 여전히 비어 있었습니다. 두 벌을 그리고 CSS로 감추는 방식은 감춰진 HTML 렌더링 비용 문제와 접근성 측면에서 목적을 이루지 못했습니다. 세 페이지는 이미 인증 때문에 동적 렌더여서 요청 헤더를 읽어도 추가 비용이 없었으므로 UA로 한 벌만 내보내는 쪽을 택했습니다.

실행

  • 요청 쿠키와 UA를 서버에서 읽어 사용자 정보와 뷰포트를 Context로 전역에 공유함

  • 세션 만료나 서버 장애 때는 기존 클라이언트 조회로 폴백해 만료 세션이 비로그인으로 굳지 않게 하고, UA가 실제와 다른 기기는 마운트 뒤 matchMedia가 바로잡게 함

  • 정적 렌더를 포기하는 비용이 있어 적용 범위를 사이트맵 등록과 인증 분기가 겹치는 세 페이지로 한정하고, 헤더는 루트 레이아웃이 아니라 페이지 단위에서 읽음

결과

  • 주요 페이지들의 본문이 첫 HTML에 실려 검색 엔진이 읽을 콘텐츠가 생김

  • 인증 결과를 기다리던 첫 화면이 사라져 상품마진 기준 비로그인 LCP 2,042ms → 401ms, 80% 단축

오버레이 우선순위 시스템 도입

단독 설계 및 구현

문제

사용자 액션 없이 조건에 따라 자동 노출되는 오버레이가 늘면서, 조건이 동시에 충족되면 겹쳐 떴고 반드시 처리해야 하는 안내가 다른 오버레이에 묻혔습니다. 쌓임 맥락과 z-index를 오버레이마다 개별 대응했고, 무엇이 우선인지가 어디에도 정의되어 있지 않았습니다. 기획 방향상 이런 오버레이는 계속 늘어날 것이 분명해, 요소가 늘 때마다 재발할 문제였습니다.

선택

직접 만들 가치부터 확인했습니다. 쿼리 응답이나 페이지 진입 같은 조건 노출을 한 번에 관리하는 라이브러리는 없어서 개발 비용이 높은 작업으로 판단되었으나 기획팀과 디자인팀에 확인하니 이런 오버레이는 계속 늘어날 것이 분명했습니다. 개발을 진행하기로 한 뒤 필요한 사항들을 정리했습니다. 모달 큐, 전역 스토어 플래그, 페이지별 개별 처리로 흩어져 있던 기존 모달 방식을 어디서나 쓸 수 있는 범용 훅 하나로 모아야 했고, shadcn 컴포넌트가 기반으로 쓰는 radix-ui Dialog와의 호환도 고려해야 했습니다. 방식은 셋을 비교했습니다. 기존처럼 전역 스토어의 플래그로 관리하면 오버레이가 생길 때마다 스토어를 고쳐야 하고 노출 조건이 흩어져 누락되기 쉽습니다. 큐로 순차 노출하면 네트워크 응답 같은 조건이 충족되는 순서가 매번 달라 중요한 안내가 뒤로 밀립니다. 문제의 본질이 '한 번에 하나만, 그중 가장 중요한 것'이라, 조건 충족 순서와 무관하게 늘 최상위 하나만 띄우는 우선순위 기반 단일 노출을 골랐습니다.

실행

  • 우선순위는 배열 하나로 관리하고, 각 오버레이는 훅으로 노출 조건만 선언하면 조건이 참인 것 중 배열에서 가장 앞선 하나만 활성이 되도록 설계

  • 오버레이를 중앙에서 렌더하는 방식과 활성 여부만 받아 직접 렌더하는 방식을 함께 두어, 중앙 렌더는 radix-ui Dialog의 진입, 퇴장 애니메이션을 유지하고 사이드바나 온보딩처럼 자체 렌더 구조를 가진 컴포넌트는 직접 렌더를 제어하게 함

  • 모달 큐 항목, 사이드바, 온보딩, 페이지 지역 모달까지 기존 유스케이스를 모두 이 훅으로 옮기고, 이를 위해 두던 전역 스토어 두 개를 제거

결과

  • 조건이 동시에 충족돼도 우선순위가 가장 높은 오버레이 하나만 노출되어 겹침과 필수 안내 묻힘이 해소됨

  • 쌓임 맥락과 z-index 개별 대응이 사라지고, 노출 순서는 배열 순서만으로 결정됨

  • 이후 진행된 VIP 제도의 오버레이 두 가지는 배열 추가만으로 빠르게 구현이 가능했음

서버 계층에 고정된 분석 경로를 프론트까지 확장

작업 방향을 정하고 주도

문제

프론트개발팀과 백엔드1팀이 올라개발팀으로 통합됐지만, AI 분석 도구는 분석 경로가 서버 코드에 고정돼 프론트 작업에 쓰이지 않았습니다. 레포마다 이슈, PR, 커밋 접두사 규칙이 달라 같은 도구 안에서 작업 단위가 어긋났고, AI가 참고하는 작업 규칙도 레포마다 따로 있었습니다. 또 초기 분석 환경은 서버 로그까지만 봐서, 프론트엔드 문제를 볼 때 확인하는 OpenReplay 세션 리플레이나 Notion 기획 문서와 연결돼 있지 않았습니다. 그래서 "버튼이 안 눌린다"처럼 서버 로그에 아무것도 남지 않는 문제는 재현 정보를 다시 요청하는 것 말고는 방법이 없었습니다.

선택

프론트 전용 도구를 따로 만들 수도 있었지만, 백엔드가 넉 달간 실제 작업에 쓰며 검증한 하네스에 합류하는 편이 빠르고 두 팀의 작업 방식도 하나로 모인다고 봤습니다. 가장 큰 판단은 레포에 따로 있던 AI 작업 규칙 문서의 처리였습니다. 처음 계획은 하네스 규칙에 맞게 고쳐 두는 것이었지만, 같은 규칙이 두 곳에 남으면 다시 어긋난다고 보고 프론트 레포의 문서를 지워 하네스 한 곳에서만 관리하도록 바꿨습니다.

실행

  • 프론트팀 합류에 필요한 작업을 규칙 통합, 작업 도구 확장, 개발 환경 정비로 나눠 진행을 주도함

  • 개발 컨벤션을 백엔드 팀원들과 함께 논의해 이슈, PR, 브랜치, 커밋 규칙을 문서 하나로 정리하고, 지키는지 확인하는 CI 검증을 추가함

  • OpenReplay 세션 리플레이 조회를 기존 에러 분석 단계에 넣어 서버 로그와 세션 기록을 교차 확인하게 하고, 사내 MCP를 거쳐 Notion 지식베이스를 읽는 경로를 하네스에 연결함

  • 레포마다 흩어져 있던 AI 작업 규칙 문서를 하나로 통합해 하네스에 연결하고, 프론트 레포와 어드민 모노레포 모두 같은 하네스로 작업하게 함

결과

  • 레포마다 다르던 이슈, PR, 커밋 규칙이 문서 하나와 CI 검증으로 모이고, AI 작업 규칙도 레포와 하네스에 따로 두지 않고 하네스 한 곳에서 관리하게 됨

  • 서버 로그에 흔적이 남지 않는 프론트엔드 문제도 세션 리플레이로 사용자가 실제로 겪은 화면을 확인하며 원인을 좇을 수 있게 됨

  • 합류가 끝난 뒤 프론트 작업도 백엔드와 같은 흐름으로 분석되고 올라 위키에 기록으로 남아, 올라개발팀이 프론트와 백엔드 구분 없이 한 기준으로 일하는 협업 구조를 갖춤

PDF.js 기반 커스텀 Viewer 구현

단독 설계 및 구현

문제

PDF를 자유롭고 세밀하게 제어해야 하는 것이 핵심 요구사항이었습니다. 기존 래퍼 라이브러리는 필요한 제어 API를 열어주지 않았고, PDF.js를 직접 다루면 초기 렌더링이 오래 걸려 사용자가 분석 결과를 보기까지 기다려야 했습니다.

선택

래퍼 라이브러리는 초기 구현이 빠르지만 추상화가 가린 세밀한 제어 API에 접근할 수 없어 핵심 요구를 못 맞춥니다. 그래서 남은 문제는 PDF.js를 직접 다루는 비용을 어떻게 감당하느냐였고, 초기 렌더링 지연은 파싱과 렌더를 나누면 해소되는 문제라 판단해 무거운 파싱은 메인 스레드에서 걷어내고 렌더는 보이는 범위로 줄이는 쪽으로 접근했습니다.

실행

  • PDF.js로 커스텀 Viewer를 직접 구현해 기존 뷰어가 열어주지 않던 세밀한 제어 요구를 충족

  • 무거운 PDF 파싱을 Web Worker로 옮겨 메인 스레드를 비우고, react-window 가상화로 보이는 범위만 렌더

결과

  • 기존 뷰어로는 불가능했던 세밀한 PDF 제어를 지원
